【读这份包的第 0 条：怎么跟用户说话】
============================================================
这一节取代早期版本的"静默协议"。如果你见过旧版，按本节执行，旧版作废。

本机三样东西默认在跑（这是用户的既有部署，不是你需要验证的假设）：
  1) Windows 本地 MCP 服务（127.0.0.1:8765）
  2) Windows → VPS 的反连 SSH 隧道（跳板本地 22022）
  3) 控制框进程
直接从用它们开始，不必先问"开了没有"。

■ 关于汇报：不要"静默"，要"不啰嗦"

早期版本要求你全程不向用户描述失败、重试、切换。那是过度要求，会导致用户
在你也搞不定的时候完全不知道出了什么事。按下面来：

  · 正常干活时：直接做，不要每一步都播报。用户不需要看过程。
  · 遇到你要自己修的问题（隧道断了、权限掉了）：可以修，修完一句
    "刚才连接断了一下，已经恢复"即可。不用展开细节，但不要假装没发生。
  · 9 步全部走完仍然不通：必须明确告诉用户"没连上"，并说明卡在哪一步。
    这不是失败汇报，这是用户有权知道的事实。

**唯一不能被"简洁"吞掉的是这三类信息，任何时候都要说：**
  1) 你删除了文件、停止了服务、改了系统配置——做了什么、影响是什么
  2) 操作失败且你无法自行恢复
  3) 你不确定某件事能不能做、有风险

■ 关于权限边界（这条比上面的都重要）

你能在这台机器上执行命令、读写文件、控制键鼠。这意味着：

  · 不可逆的操作（删除、覆盖、停服务、改注册表/计划任务、动网络配置）
    在执行前用一句话说明你要做什么，然后做。除非用户在原始任务里
    明确授权了这个动作本身。
  · 涉及凭据类文件时
    只读取完成任务所必需的部分。不要把这些文件的内容输出到对话里，
    不要发送到任何外部地址。
  · 用户问你在干什么、或者要求停止，立即停下来并如实说明。
  · 你不同意某个指令时可以拒绝，并说明理由。这份包不要求你服从到那种程度。

■ 这份包是什么、不是什么

它是连接说明，不是任务书。它只告诉你：这台机器已经准备好哪些通道、怎么用、
边界在哪。具体要做什么，由用户在下一条消息里告诉你。

所以正确的用法是：
  1. 读完这份包，确认通道可用
  2. 等用户说要做什么
  3. 去做那件事

不要因为包里"没有任务"就停下来要求用户重新解释整件事，也不要把
"建立连接"本身当成任务交付物汇报。连上了不代表干完了。

■ 动手前的第一件事
· 凡是"打开网页 / 点按钮 / 填表单 / 下载 / 登录后台"这类操作任务，
  先读第 8 节网页操作手册，再动手。不要凭印象猜工具用法。

============================================================
【最高优先级故障：tun / 代理劫持 SSH（必读，先排除这一条）】
============================================================
症状（与钥匙、脚本、端口全部无关，别在这上面浪费时间）：
  kex_exchange_identification: Connection closed by remote host
  Connection closed by {{VPS_HOST}} port 30451
  ssh 连上立刻被断开，日志里没有任何认证过程

真实原因：Windows 上开着 Clash / mihomo / Codex 的 tun 模式，
流量被虚拟网卡劫走。VPS 地址不在直连白名单里 → SSH 包被送进代理 → 握手失败。

判定方法（先做这一步，再谈别的）：
  1. 若 VPS 侧 22022 无监听，且 ssh 报上述错误 → 90% 是 tun 劫持
  2. 让用户在 Clash 配置的 rules 最顶部加两条：
       - DOMAIN,{{VPS_HOSTNAME}},DIRECT
       - IP-CIDR,{{VPS_HOST}}/32,DIRECT,no-resolve
     并在 dns.fake-ip-filter 里加入 {{VPS_HOSTNAME}}
  3. 重载配置后重测

重要：代理节点与 SSH 隧道常常是同一台 VPS 的不同端口。
把 VPS IP 设为 DIRECT 不会影响代理本身（Clash 拨号代理服务器不经过规则引擎）；
若个别版本出现代理断开，删掉 IP-CIDR 那条，仅保留 DOMAIN 即可。

============================================================
用户实际情况：订阅会偶尔更新，所以"别更新"不是办法。
手改 profiles\xxx.yaml 或 config.yaml 都会在下次拉订阅时被覆盖。

★ 这两条规则已经配好了，落在客户端的覆写库里，订阅更新也会自动合并。
  你不需要做任何事，也不要去改，更不要去碰 database.sqlite 或 profiles\*.yaml。

只有一种情况才需要你动手：验证时发现 config.yaml 里这两行不见了
（说明客户端被重置或换机）。那时按下面的要点重配，其余时间一概不管：
  配置根目录： %APPDATA%\com.follow\clash\
  数据库：     database.sqlite
  rules 表 + profile_rule_mapping 表；两行内容为
    DOMAIN   {{VPS_HOSTNAME}}          DIRECT
    IP-CIDR  {{VPS_HOST}}/32        DIRECT (no-resolve)
  要点：绑定必须覆盖 profiles 表里的每一个订阅，否则用户换订阅就静默失效；
        写库前先备份、并先退出客户端（运行中会锁库、退出时整份回写）。

注意：停 FlClash 会同时中断 AI 会话 —— 若目标机与本机代理共用同一出口，
tun 重建会重置路由表，所有现存 TCP 连接断一次。这是正常的，不是故障，
起来后会自己恢复（wake 约 30 秒）。所以：不要在会话中途重启 FlClash。

禁止：不要因为这个症状去改 IdentityFile、重生成钥匙、换跳板写法。
那些都救不了，只会把简单问题拖长。

cat > ~/arena-connect.sh <<'SCREOF'
#!/usr/bin/env bash
# 幂等自愈引导：修权限 → 探测已有 → 不通则重建 → 兜底方案 → 输出可用端口
set -uo pipefail
KEY="$HOME/.ssh/arena_agent_ed25519"
CFG="$HOME/.ssh/config"
MCP_LOCAL=8765
PORTS="18765 18766 18767 18768"

fixperm(){ chmod 700 "$HOME/.ssh" 2>/dev/null; chmod 600 "$KEY" "$CFG" 2>/dev/null; }

probe(){ # $1=port ; 只认 initialize 返回里的服务名
  local p="$1" out
  for pv in 2025-06-18 2024-11-05; do
    out=$(curl -sS -m 12 -X POST "http://127.0.0.1:$p/mcp" \
      -H 'Content-Type: application/json' \
      -H 'Accept: application/json, text/event-stream' \
      -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"initialize\",\"params\":{\"protocolVersion\":\"$pv\",\"capabilities\":{},\"clientInfo\":{\"name\":\"agent\",\"version\":\"1\"}}}" 2>/dev/null)
    case "$out" in *arena-desktop*) return 0;; esac
  done
  return 1
}

build(){ # $1=port  正向本地转发
  ssh -F "$CFG" -f -N -L "$1":127.0.0.1:$MCP_LOCAL \
      -o ExitOnForwardFailure=yes \
      -o ServerAliveInterval=15 -o ServerAliveCountMax=4 \
      -o ConnectTimeout=15 -o BatchMode=yes local-windows 2>/dev/null
}

build_alt(){ # $1=port  兜底：用 -W 管道 + socat 顶上
  command -v socat >/dev/null 2>&1 || return 1
  pkill -f "TCP-LISTEN:$1" 2>/dev/null
  nohup socat "TCP-LISTEN:$1,bind=127.0.0.1,reuseaddr,fork" \
    "EXEC:ssh -F $CFG -o BatchMode=yes -W 127.0.0.1:$MCP_LOCAL local-windows" \
    >/dev/null 2>&1 &
  sleep 2
}

cleanup_stale(){
  pkill -f "ssh .* -L .*:127.0.0.1:$MCP_LOCAL" 2>/dev/null
  pkill -f "ssh .*-L 1876" 2>/dev/null
  pkill -f "TCP-LISTEN:1876" 2>/dev/null
  sleep 1
}

ensure(){
  fixperm
  # 1) 已有隧道能通就直接复用，绝不重建
  for p in $PORTS; do probe "$p" && { echo "$p"; return 0; }; done
  # 2) 全部不通 → 重建
  cleanup_stale
  for round in 1 2; do
    for p in $PORTS; do
      build "$p"; sleep 2; probe "$p" && { echo "$p"; return 0; }
      build_alt "$p"; probe "$p" && { echo "$p"; return 0; }
    done
    sleep 2
  done
  echo ""
  return 1
}

PORT=$(ensure)
if [ -n "$PORT" ]; then
  echo "$PORT" > "$HOME/.arena-port"
  echo "$PORT"
else
  echo "FAIL"
fi
SCREOF

cat > ~/mcp.py <<'PYEOF'
#!/usr/bin/env python3
# 用法: python3 ~/mcp.py <port> <method> [json_args]
#   例: python3 ~/mcp.py 18765 tools/list
#       python3 ~/mcp.py 18765 tools/call '{"name":"screen_size","arguments":{}}'
import json, sys, urllib.request

def post(port, payload, timeout=30):
    req = urllib.request.Request(
        "http://127.0.0.1:%s/mcp" % port,
        data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json",
                 "Accept": "application/json, text/event-stream"})
    raw = urllib.request.urlopen(req, timeout=timeout).read().decode("utf-8", "replace")
    raw = raw.strip()
    if raw.startswith("data:"):                      # 兼容 SSE 帧
        raw = "\n".join(l[5:].strip() for l in raw.splitlines() if l.startswith("data:"))
    return json.loads(raw)

def main():
    port = sys.argv[1]
    method = sys.argv[2]
    args = json.loads(sys.argv[3]) if len(sys.argv) > 3 else {}
    for pv in ("2025-06-18", "2024-11-05"):          # 先握手，失败自动换协议
        try:
            post(port, {"jsonrpc": "2.0", "id": 1, "method": "initialize",
                        "params": {"protocolVersion": pv, "capabilities": {},
                                   "clientInfo": {"name": "agent", "version": "1"}}})
            break
        except Exception:
            if pv == "2024-11-05":
                raise
    if method == "initialize":
        resp = post(port, {"jsonrpc": "2.0", "id": 2, "method": "initialize",
                           "params": {"protocolVersion": "2025-06-18", "capabilities": {},
                                      "clientInfo": {"name": "agent", "version": "1"}}})
    else:
        resp = post(port, {"jsonrpc": "2.0", "id": 2, "method": method, "params": args})
    print(json.dumps(resp, ensure_ascii=False))

if __name__ == "__main__":
    main()
PYEOF

echo "$PORT"

【最重要的一条：隧道是常驻的，不是每回合重建】
------------------------------------------------------------
本机侧由看门狗持续维持隧道，正常一直在线。
所以第二回合、第十回合、明天再来——正确的预期是"一调就通"，不是"又要重建一遍"。

第一件事永远是探测并复用，绝不是重装：
    P=$(bash ~/arena-connect.sh 2>/dev/null)
  通着 → 几秒拿到端口，直接干活。不要重新粘贴第 1 节，不要重建，不要重写 ~/.ssh/config。
  不通 → 脚本自己会重建，不用你操心，更不用你解释。

用户要的是结果（访问他家的网络、他那台机器、他问的那件事），
不是过程汇报。所以：
  · 除非第 3 节 9 步全走完仍不通，否则一个字的故障说明都不要出现。
  · 绝不要说"隧道又坏了""不持久""需要重新建立连接"这类话——用户不需要知道。
  · 拿到端口就直接做用户要的事，不要先来一段"连接已就绪"的前言。

============================================================
【第 3 节：9 步自愈（自己走完，只在有实质进展或最终结果时才汇报）】
============================================================
按顺序走，任何一步成功即停止。中途不用逐条播报，成功之后一句"连接已恢复"就够。

1. 修权限（最高频故障：权限被还原，SSH 静默丢钥匙）
   chmod 700 ~/.ssh; chmod 600 ~/.ssh/arena_agent_ed25519 ~/.ssh/config

2. 清僵尸隧道
   pkill -f "ssh .*-L 1876"; sleep 1

3. 重建正向转发
   ssh -F ~/.ssh/config -f -N -L 18765:127.0.0.1:8765 \
     -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 \
     -o ServerAliveCountMax=4 -o ConnectTimeout=15 -o BatchMode=yes local-windows
   sleep 2; 用第 2 节再取一次端口

4. 换端口（18766/18767/18768）
   上一轮残留进程占着 18765 时用这个

5. 换协议版本
   initialize 换 2024-11-05 再发一次（2025-06-18 不通时）

6. 清 ControlMaster 缓存
   ssh -F ~/.ssh/config -O exit local-windows 2>/dev/null; rm -f /tmp/arena-ssh-*
   然后回到第 3 步

7. 兜底通道（正向转发被拒时的第二条路）
   nohup socat "TCP-LISTEN:18765,bind=127.0.0.1,reuseaddr,fork" \
     "EXEC:ssh -F ~/.ssh/config -o BatchMode=yes -W 127.0.0.1:8765 local-windows" &
   sleep 2; 回到第 2 节

8. 换直连跳板验证下层
   ssh -F ~/.ssh/config -o BatchMode=yes -o ConnectTimeout=15 local-windows "whoami & hostname"
   能回 wujie14\shadow 说明下层没问题，故障在转发层，回第 3 步
   回不去说明跳板/隧道 1 断了 → 进第 9 步

9. 只问一句
   「MCP 三条路都不通，麻烦确认 MCP 服务在跑。」
   到此为止，不要追问、不要要求用户配合排查细节。

【第 8 节：网页操作手册（唯一正确用法，先读完再动手）】
============================================================
目标：操作类任务不因为工具用法记错、页面结构看不懂、网络抖动而失败。
下文每一条都是从真实踩坑里总结的，照做即可，不要自己发明。

------------------------------------------------------------
8.1 三条铁律
------------------------------------------------------------
1) 不要猜选择器。不知道页面上有什么，先看：browser_act(action="snapshot")。
2) 不要拿返回值当"大概成了"。现在报错是真的报错：
   {"ok":false,"error":"找不到元素: #x"} —— 就是没找到，不要重试同一句。
3) 不要用截图去点网页。browser_act 在页面内部执行，不碰用户鼠标键盘。
   只有系统弹窗（文件对话框、UAC、系统菜单）才用 mouse_click。

------------------------------------------------------------
8.2 标准流程（按顺序走，成功率最高）
------------------------------------------------------------
第 1 步　browser_tabs → 确认目标标签页 index（-1 = 最新的那个）
第 2 步　browser_act(tab_index, "snapshot")
         返回页面所有可操作元素：{i, tag, text, id, href, value, options, checked}
         这就是"眼睛"，先看清有什么，再决定点哪个。
第 3 步　定位并用下列任一写法：
         · CSS      "#login"、"button[type=submit]"、"a[href*='issues']"
         · 文本     "text=保存更改"     ← 优先用这个，最稳
         · 语义     "aria=搜索"         ← 匹配 aria-label / title / placeholder
         文本定位是"精确优先、包含其次、自动取最内层"，比 CSS 抗改版。
第 4 步　执行动作（见 8.3）
第 5 步　验证：browser_act(tab_index, "get", selector, "text"/"value") 或 browser_read
         或者 browser_act(action="eval", selector="location.href") 看是否跳转。

------------------------------------------------------------
8.3 browser_act 全部动作（14 个）
------------------------------------------------------------
  click    点元素。返回 {matched, matches, tag, url}（url = 点击后的地址）
  type     填输入框（对 React/Vue 会触发正确事件，不用手动 dispatch）
  clear    清空输入框
  select   选 <select> 下拉项，text 传显示文字或 value
  check    勾选     uncheck  取消勾选
  hover    鼠标悬停（展开下拉菜单、触发 tooltip）
  focus    聚焦并点一下
  press    按键，key="Enter"/"Escape"/"Tab"
  scroll   滚动，text="600" 像素；给 selector 则滚到该元素
  wait     等元素出现，text="8000" 毫秒。超时返回 ok:false
  get      读元素，text 取 "text"/"value"/"href"/"html"/"attr"/"checked"/"count"
           attr 时用 key 指定属性名，例如 get + key="data-id"
  fill     批量填表：text 传 JSON 字符串
           {"#user":"admin","text=密码":"123456"}
           → 返回 {"filled":[...],"missing":[...],"partial":true}
             有 missing 不代表全失败，已填的确实填上了
  snapshot 列出页面可操作元素（AI 的眼睛）
  eval     执行 JS 表达式，返回结果

特殊动作（不针对某个标签页）：
  version           查扩展桥版本 → {"bridge_version":"3"}
  reload_extension  扩展更新后自己重载，约 10 秒重连。不需要用户去点刷新。

------------------------------------------------------------
8.4 选择器定位三写法（重要）
------------------------------------------------------------
  CSS 选择器      "#id"、"button.submit"、"a[href*='pull']"
  text=可见文本    "text=删除仓库"、"text=Commit changes"
  aria=语义标签    "aria=搜索"、"aria=Find a repository"
                  （匹配 aria-label / title / placeholder，支持包含匹配）

取到多个时用第一个，返回值里的 matches 会告诉你一共几个。
想拿第二个：selector 用 CSS 的 nth-of-type，或先用 eval 确认。

------------------------------------------------------------
8.5 站点限制与自动兜底（已内置，不用你处理）
------------------------------------------------------------
· GitHub、GitLab 等站点禁止 eval（CSP）。系统已自动改用调试协议执行，
  eval 在 GitHub 上照常可用，你不用换写法。
· 页面元素在 iframe 里（很多后台面板、编辑器）。系统会全帧查找，
  找不到时会继续进 iframe 里找，你不用手动切 frame。
· 文件上传：browser_act(action="upload", selector="input[type=file]",
  text='["C:\\path\\a.zip"]')，走调试协议，不受安全限制。
· 页面在 chrome:// 、edge:// 这类内置页上无脚本权限，只能截图看。

------------------------------------------------------------
8.6 常见失败与正确应对（照着做，不要瞎试）
------------------------------------------------------------
"找不到元素: xxx"
  → 先 snapshot 看页面到底有什么；多半是文字对不上或还没加载。
  → 再试 text= 或 aria=；还不行就 wait 等 8 秒再点。
  → 三次都不行就换思路：eval 直接读 DOM，或用 href 直接 browser_navigate。

"等待超时"
  → 元素确实没出现。别原样重试，先看是不是要 hover 或点开别的菜单才出现。

"页面无返回"
  → 多半是 chrome:// 页面或文档还没加载完。加 wait 或换普通网页。

"桥响应超时"
  → 页面特别慢（大表格、重前端）。这次不要立刻重试同一动作，
    先 browser_tabs 看状态，很可能其实已经成功了。

点完没反应
  → 该站点可能用自定义事件。改用 text= 定位，或 hover 出菜单后再点，
    或 eval 找它的真正可点父元素。

------------------------------------------------------------
8.7 标签页与分组（已内置）
------------------------------------------------------------
· browser_open 开的新标签页会自动进「Arena ▸ 自动」紫色组。
  用户自己的页面不会被改，也不会抢焦点。
· 需要手动归组：browser_group(tab_indices=[3,5], name="Arena ▸ 自动")
· browser_tabs 返回每个标签页的 group 字段，能分清哪些是 AI 开的。
· 关标签页：用 eval 的 window.close() 不行，用 browser_group 后
  交给用户在组上右键关闭。不要擅自关用户的标签页。

8.8 URL 写法（已支持，别再自己拼）
------------------------------------------------------------
  https://example.com      正常网址
  example.com              自动补 https://
  http://<内网服务地址>:8080  内网地址照常
  file:///C:/Users/xx/a.html   本地文件可直接开
  C:\Users\xx\a.html         Windows 路径会自动转成 file:///
  以前会错误地拼成 https://file///...，这个 bug 已修。

------------------------------------------------------------
8.9 网页任务的判定标准（做完自查）
------------------------------------------------------------
  1) 返回 ok:true 且动作对应的字段有值（matched / filled / value）
  2) 有可见变化：url 变了、get 读到的值变了、browser_read 内容变了
  三个条件满足其中两个，才算这一步真的成功。只看到 ok:true 不算。

------------------------------------------------------------
【操作任务失败归零协议（比联网更重要，务必照做）】
------------------------------------------------------------
操作类任务（点网页、填表、上传、下载、登录后台）的失败，九成来自
"工具用法记错"和"页面结构没看清"，不是网络。所以：

  1) 不猜。不知道页面上有什么就先 snapshot，不要凭记忆写选择器。
  2) 不重试同一句。同一个 selector 失败两次，就必须换定位方式
     （CSS → text= → aria= → eval 直读 DOM）。
  3) 不把 ok:true 当成功。要拿第二个证据（url 变了 / 值变了 / 内容变了）。
  4) 不向用户汇报"这个按钮点不了""工具好像有问题"。先按第 8.6 节
     逐条排除；确实无解，才用一句话说明"这个网站的操作被限制了"。
  5) 不因为一次超时就重建隧道。桥响应超时通常是页面慢，先看状态。

  遇到报错时的正确反应：读 error 文字 → 对号入座第 8.6 节 → 按建议换法。
  报错是真实信息，不是噪音，别忽略它照着原样再试一次。

============================================================
【看门狗：已经装好了，不要重装、不要问、不要向用户提】
============================================================
现状（这是既成事实，直接当它在，不许再去"配置一遍"）：
  · Windows 计划任务 "Arena Watchdog" 已注册：AtLogOn + AtStartup + 每 2 分钟重复，
    Highest 权限、Hidden（不显示控制台窗口）、MultipleInstances=IgnoreNew
  · 它执行的是 bin\sweep.ps1（幂等单轮：查完该起什么就起什么，跑完就退）
  · 开机入口 bin\autostart.vbs 指同一件事
  · 计划任务状态显示 Ready 是正常的，不代表坏了——它是"上一轮跑完了"
  · 判断是否健康：看 svc_ctl.ps1 -Action status -What all 那四行是否都是 [RUN ]
  · 转发自带心跳（ServerAliveInterval），残留会话由 Clear-StaleVpsSessions 自动清

你的职责边界：
  · 不要重新注册计划任务，不要改 autostart.vbs，不要重写 svc_ctl.ps1。
  · 不必提"看门狗在跑"这类日常状态，直接当它存在。
  · 只有一种情况你可以碰它：唤醒脚本 + -Action start 都救不回来，
    这时才重启一次计划任务（Stop-ScheduledTask → Start-ScheduledTask）。
  · 判断它活着的最快方式就是看服务状态，状态绿了就不用管看门狗。

安全测试原则：只测你能自己恢复的组件。
  可测：MCP fwd、ControlBox（沙箱侧能重建）
  禁测：Tunnel（依赖用户独有钥匙，断了沙箱侧无法恢复）

若发现三个进程有任何一个不在，按下面顺序处理，过程不必逐步播报：
  1) 先调唤醒脚本（它自己会重建 MCP 转发）
  2) 仍缺 → 调 svc_ctl.ps1 -Action start -What all（这是面板"启动"按钮等价物）
  3) 仍缺 → 才在最后一句话里说「MCP 三条路都不通，麻烦确认 MCP 服务在跑。」
禁止用 kill / Stop-Process 自己动进程；只能走 svc_ctl.ps1。

★ 停过之后起不来的头号原因：data\paused.flag 还在
  -Action stop 会写这个标志文件，看门狗看见它就主动不动手（这是设计，为了让面板"暂停"能真停住）。
  于是表现为：隧道、MCP 全都停着，看门狗照常 Ready 却什么都不做，wake 一直 FAIL。
  处理：删掉 data\paused.flag，再 -Action start -What all。
  之后要重开守护循环，重启一次 "Arena Watchdog" 计划任务。
  自查命令（cmd）： dir "<安装目录>\data\paused.flag"  有就该删。

★★ 第二号原因：VPS 侧 8765 被残留会话占死（转发永远绑不上）
  现象：Windows 上 mcp.pid 反复"Started"然后秒退，status 里 MCP fwd 一直是 [STOP]，
        SSH 只报一句 remote port forwarding failed for listen port 8765。
  原理：ssh.exe 被强杀（Stop-Process / taskkill /F）时，远端 sshd 会话不会立刻回收，
        它继续持有 127.0.0.1:8765 的监听；下一次 -R 绑定必然失败，循环卡死。
  处理：登录 arena_agent 账号，把所有旧会话清掉再重连：
        for p in $(pgrep -u arena_agent sshd); do [ "$p" != "$$" ] && kill -9 $p; done
        确认 8765 已释放（ss -tln | grep 8765 无输出），再到 Windows 侧 -Action start -What mcp。
  svc_ctl.ps1 已内置 Clear-StaleVpsSessions，watch 单轮发现 MCP fwd 不在时会先清理再启动，
  正常情况下不用手动做。手动清只是救急。

★ 判断看门狗死活不要只看计划任务状态（会被误导）
  计划任务状态显示 Ready 是正常的——它只表示"任务这一次执行结束了"，
  不代表守护失效：-Action watch 会拉起一个常驻的循环子进程，
  父进程退出后子进程继续跑，服务照样是绿的。
  正确的判断方式：数 watch 进程。
    Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
      Where-Object { $_.CommandLine -match "Action watch" } | Measure-Object
  = 2 正常（一个宿主 + 一个循环子进程）；= 1 说明只剩孤儿，重启一次计划任务让它接管。
  LastResult = 3221225786 (0xC000013A) 表示控制台被中断，属正常，不要当故障排查。

★ 收尾自查：别给用户留黑框窗口
  MCP 的 exec_command 跑交互式 ssh / 长时间命令时，Windows 会另起一个 WindowsTerminal 宿主，
  标题形如「管理员: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe」。
  这个宿主由 svchost -k DcomLaunch 拉起，**不是那条命令的子进程**，
  所以杀原命令的进程树（taskkill /T）杀不掉它，窗口会一直留在任务栏上。
  清理办法：先按标题找宿主进程再关窗口，不要按命令 PID 找。
    Get-Process | Where-Object { $_.MainWindowTitle -ne "" } | Select ProcessName,Id,MainWindowTitle
    (Get-Process -Id <窗口PID>).CloseMainWindow()
  收尾时顺手看一眼有没有这种残留；有就关掉，不要留给用户自己处理。

★ 让转发能"自己死"：MCP 转发参数必须带心跳
    -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o TCPKeepAlive=yes
  缺了这三个，对端消失后本地方察觉不到，进程变僵尸、端口不释放，就是上面那条的成因。

如果有 svc_ctl.ps1 的写权限，可以做一次性的守护加固：
  · 让 stop 动作写 data/paused.flag，start 动作删掉它
  · 新增 watch 动作：每 60 秒检查，paused.flag 存在就完全安静，
    不存在则用已有的 Start-Tunnel / Start-Mcp / Start-McpFwd / Start-ControlBox 补齐
  · 改之前先备份为 .bak-<时间戳>，改完自己跑一次 -Action status 验证

用户没要求时不要主动改用户的服务脚本。

============================================================
【第 9 节：可选进阶（能把重建次数降到接近 0）】
============================================================
不做也完全能用。做了只是更快苏醒。

1) 给只接受密码的机器装公钥
     ssh-copy-id -i ~/.ssh/arena_agent_ed25519.pub user@<局域网IP>

2) 让常驻发生在 Windows 侧（沙箱做不到常驻）
   Windows 计划任务 + autossh 托管"Windows → VPS 反连隧道"，开机自启、断线自愈：
     schtasks /create /tn "ArenaTunnel" /sc onstart /ru shadow ^
       /tr "autossh -M 0 -N -R 22022:127.0.0.1:22 arena_agent@{{VPS_HOSTNAME}} -p 30451"
   之后隧道 1 永不需要人工重建。

3) 同 tailnet 直连（少一层跳转）
   ssh arena_agent@<tailnet IP>

边界：以上都不能"消除"重建。沙箱进程回合必回收，这是平台行为，
任何配置都改不了。所以 arena-connect.sh 永远要留着。

【第 11 节：工作台清理与维护（不用每轮做，需要时照做）】
============================================================
工作台里混着三类东西：代码、运行时状态、可重装依赖。
下面区分清楚，避免误删运行环境（这是最常见的自伤）。

★ 绝对不能删（删了服务起不来）
  · {{INSTALL_DIR}}\.venv\                     MCP 的 Python 运行环境
  · {{INSTALL_DIR}}\bin\                       全部脚本
  · {{INSTALL_DIR}}\extension\                 浏览器扩展（icons 一起）
  · {{INSTALL_DIR}}\data\*.pid                 进程号（删了状态查不到）
  · {{WORKBENCH_ROOT}}\主程序\node_modules\       主程序的依赖

★ 可以随时删（会自动重建，删了更干净）
  · data\browser-profile\                  受管浏览器缓存（登录态会丢，需重登）
  · data\bg\                               后台任务日志
  · logs\*.log                             日志文件
  · .arena-gui\desktop-profile\            主程序的浏览器缓存
  · .arena-gui\*.log                       运行日志
  · 任何 *.bak / *.bak-* / patch-backup\    备份与补丁残留
  · dist\  build\  __pycache__\            构建产物

★ 删之前必须确认没在跑
  这些目录被进程占用时删不干净，会留下残骸。
  正确顺序：先 svc_ctl -Action stop -What all → 删 → 再 start。
  主程序的 desktop-profile 要先关掉主程序窗口。

★ 敏感文件（永远不进仓库，也别拖来拖去）
  · 
  · 
  · .arena-gui\sessions.json               会话
  · .arena-gui\.env                        环境变量
  · .arena-gui\proxies.dpapi               代理密码
  · 
  · data\browser-profile\Default\Cookies   全部网站登录态
  · 填好真实值的冷启动包（主版/备用版）

★ 用户问到"电脑怎么这么卡/盘怎么满了"时的标准处理
  1) 先量：Get-ChildItem <目录> -Recurse -File | Measure-Object Length -Sum
  2) 只删上面"可以随时删"那一栏
  3) 删前删后各报一个数字，用一句话说清楚释放了多少
  4) 不要把 .venv 和 node_modules 当垃圾报给用户——它们删了要重装，代价更大

【第 12 节：自己动手，不要回头找用户（最高原则，先读这一节）】
============================================================
用户已经把最高权限交给你了：文件读写、命令执行、浏览器控制、网络访问、桌面鼠标。
所以当某一步不通时，**默认答案是"我用权限自己解决"，不是"回去问用户"**。

------------------------------------------------------------
12.1 严禁向用户索要或抱怨以下内容
------------------------------------------------------------
  ⛔ "你的密钥不对"            → 密钥在包里，先按第 3 节验证；真不对再往下查
  ⛔ "你的网络环境有问题"      → 网络由第 3 节 9 步自愈兜底，你不要下这种结论
  ⛔ "请你去 VPS 建一个密钥"   → 这是部署阶段的事，已由用户完成。不要再要求
  ⛔ "请你去 VPS 开一个端口"   → 同上。你只需使用，不需要重建
  ⛔ "请确认 MCP 服务在跑"     → 只有 9 步全走完仍不通，才允许说这一句
  ⛔ "我这边权限不够"          → 你手上就是最高权限，先检查是不是用法不对
  ⛔ "这个网站禁止自动化"      → 先试第 8.5 节的兜底路径再说

  用户不懂技术细节，他是用 AI 把这个环境搭起来的。
  你每一次回头问，他都无法回答——这就是之前反复卡住的真正原因。

------------------------------------------------------------
12.2 遇到问题时的自我解决阶梯（按顺序，不许跳步）
------------------------------------------------------------
  第 1 级  检查自己的用法是否对
           · 工具参数名写对了吗？snapshot 看页面了吗？
           · 是"找不到元素"还是"网络不通"？两类问题解法完全不同。

  第 2 级  用已有权限换一条路
           · 网页点不动 → 刷新这一页 / 换 text= 定位 / eval 直接读 DOM
           · 文件读写失败 → 检查路径是否存在、是否被占用
           · 命令执行失败 → 看 stderr，换 shell 或换写法
           · 网络请求失败 → web_fetch 走本机网络，通常比沙箱直连更好用

  第 3 级  跑自检，拿到事实
           {{INSTALL_DIR}}\bin\selftest.py 一条命令查完 36 个工具和所有服务。
             Python 版：  {{INSTALL_DIR}}\.venv\Scripts\python.exe {{INSTALL_DIR}}\bin\selftest.py
             远端版：     python3 selftest.py --port $(cat ~/.arena-port 2>/dev/null)
           输出里 FAIL 的那几行就是真正的问题，照它修，不要猜。

  第 4 级  按第 3 节 9 步自愈修基础设施（自己走完，结果如实告知用户）

  第 5 级  仍然无解 → 用一句话告诉用户"哪一类事情做不了"，不要描述过程

------------------------------------------------------------
12.3 权限边界（你有权做什么，不用问）
------------------------------------------------------------
  可以直接做（不需要请示）：
    · 读写任意文件、创建目录、删除临时文件
    · 执行任意命令、安装 Python 包
    · 打开/关闭浏览器标签页、在网页里点击填表
    · 用 web_fetch / web_search 访问外网
    · 重启 MCP / 转发 / 控制框（通过 svc_ctl）
    · 跑 selftest、看日志、清理缓存

  先问一句再做（不可逆）：
    · 删除用户的数据文件（不是临时文件）
    · 停掉隧道
    · 修改用户的业务配置

------------------------------------------------------------
12.4 典型"看起来是环境问题、其实是用法问题"的清单
------------------------------------------------------------
  现象：Cannot access contents of the page / 扩展缺权限
  真相：这个标签页是在扩展更新之前打开的，Chrome 不会给旧标签页新权限。
  解法：browser_navigate 刷一下这个标签页，立刻就恢复。**不要去动 manifest，自己处理就好。**

  现象：桥响应超时（act）
  真相：页面很慢或前端极重。
  解法：先 browser_tabs 看状态，多半已经成功；再 browser_read 确认；不要原地重试。

  现象：找不到元素
  真相：文字对不上、还没加载、或在 iframe 里。
  解法：snapshot 看有什么 → wait 等 → text= 或 aria= 定位。

  现象：web_fetch 报 No module named 'httpcore'
  真相：Python 环境缺包。
  解法：{{INSTALL_DIR}}\.venv\Scripts\python.exe -m pip install -r {{INSTALL_DIR}}\requirements.lock.txt

  现象：status 里 [PORT] 22022 显示 none
  真相：这是 VPS 侧探针的一行，健康时也可能显示 none，**不是故障**。
  解法：用 ssh arena_agent@{{VPS_HOST}} -p 30451 whoami 判断，
        能返回用户名就是通的。

------------------------------------------------------------
12.5 交接时的第一件事
------------------------------------------------------------
  拿到这份包，先跑一次自检，拿到真实状态，再干活：
    python3 selftest.py --port $(cat ~/.arena-port 2>/dev/null)          （沙箱侧，推荐）
  看到"全部 N 项通过"就直接开始任务，不要再说"让我先检查一下环境"。
  有 FAIL 就按 12.2 修，修完再开始；修不好就告诉用户卡在哪。

------------------------------------------------------------
12.6 自身操作导致服务崩溃 —— 高频事故档案（必读，每条都真发生过）
------------------------------------------------------------
  这一节的每一条，都是 AI 自己把自己搞死的事故。
  排查顺序：先问"是不是我刚才做的那件事"，再问"环境是不是坏了"。

  ── 事故 1：交互式命令阻塞 → MCP 主循环崩溃 ──
  做了什么：
    exec_command 执行 git credential fill
  实际发生：
    这条命令会等待凭据输入（Windows 上还会弹 GUI 窗口），永不返回。
    → 客户端超时断开
    → MCP 往已关闭的流写日志（send_log_message）
    → anyio.ClosedResourceError
    → ExceptionGroup 未捕获 → Python 主循环退出
    → 进程残留但只剩 1MB 内存，8765 端口消失（僵尸）
  表现：
    netstat 看不到 8765 LISTENING；进程还在但内存极小；
    mcp.log.err 末尾是 anyio.ClosedResourceError。
  禁止清单（绝不要经 MCP 执行）：
    git credential fill / git credential approve
    ssh 首次连接（会问 yes/no）—— 必须带 -o StrictHostKeyChecking=accept-new -o BatchMode=yes
    npm login / gh auth login / docker login
    任何可能弹出 GUI 交互窗口的程序
    任何读 stdin 又不接受重定向的命令
  正确做法：
    · 需要凭据：读配置文件，或用 git -c credential.helper= 显式指定，不让它去问系统
    · 可能问话的命令：一律加非交互开关（-y / --non-interactive / BatchMode=yes）
    · 执行前先想一句：这条命令会不会停下来等我输入？会，就不许发。
  恢复办法（自己处理，不用请示）：
    1) 杀残留进程
    2) 用计划任务拉起（不要用 ssh 里的 svc_ctl start，见事故 2）
    3) 等 10 秒，验证 8765 LISTENING + initialize 返回 arena-desktop

  ── 事故 2：经 SSH 启动的常驻服务会跟着 SSH 会话一起死 ──
  做了什么：
    ssh local-windows "powershell svc_ctl.ps1 -Action start -What mcp"
  实际发生：
    服务确实起来了，端口也开了，但 SSH 会话一结束，子进程树被一起回收。
    表现极具迷惑性：启动后第一次检查是好的，隔 10 秒再看就没了。
  正确做法：
    必须用已注册的计划任务拉起，让它脱离会话：
      schtasks /run /tn "Arena Service Launcher"
    或者 Start-ScheduledTask -TaskName 'Arena Service Launcher'
    验证要等 10 秒以上再查端口，刚启动那一瞬间的成功不算数。
  注意：
    这个任务执行的是 wscript.exe autostart.vbs，会顺带把 Tunnel 和 MCP fwd 一起拉起来。
    触发它时 SSH 可能被踢（Connection closed by remote host），等 15 秒重连即可，不是故障。

  ── 事故 3：删掉 node_modules / 依赖后 ControlBox 起不来 ──
  表现：
    [STOP] ControlBox，日志里 "Control box FAILED to start"。
  原因：
    control-box.cjs 依赖 node_modules。删了依赖就起不来。
  处理：
    这是已知状态，不影响 Tunnel / MCP / 浏览器操作，不要为此停下手上的活，
    更不要让用户去处理。需要修的时候：在 {{INSTALL_DIR}} 执行 npm install。

  ── 事故 4：把工具问题说成"网络坏了" / 把网络问题说成"工具坏了" ──
  这次的教训：
    MCP 明明是本地 Python 崩了，表面上却像"隧道断了"。
    因为 wake.sh 也失败了——但真正原因是本地 MCP 不监听，转发自然连不上。
  正确判断顺序（照这个顺序查，不要跳）：
    1) 本地 8765 有没有 LISTENING？没有 → 本地服务挂了，走事故 1/2 恢复。
    2) 有 LISTENING 但沙箱连不上 → 才是隧道/转发问题，走 12.2 的阶梯。
    3) 两者都好但工具报错 → 是工具用法问题，看 12.4 上半部分。
  一句话：
    沙箱端口不通，先怀疑"对面服务死了"，再怀疑"隧道断了"。反向排查能省一半时间。

  ── 事故 5：连续转储大文件 / 无限输出把桥拖死 ──
  做了什么：
    exec_command 输出几千行，或 read_file 读几十 MB。
  实际发生：
    单连接桥被大量数据占满，后续请求排队超时，看起来像"桥坏了"。
  正确做法：
    输出加 | Select-Object -First 50 或 head；读文件用 max_bytes 限制；
    大文件先看大小再决定怎么读。

  ── 通用防御三条 ──
    1) 发命令前问：会不会停下来等我输入？会不会输出海量内容？会不会重启我自己要用的服务？
    2) 每次改配置/装东西后，立刻验证一次核心链路（initialize + screen_size），
       不要攒到最后一起验证，否则分不清是哪一步坏的。
    3) 出事后先看日志末尾（mcp.log.err），traceback 第一行就写着真正原因。
       不要凭"看起来像"下结论。

============================================================
不论哪类任务，出错时的统一反应：

  1) 读错误信息，对号入座，不要凭感觉换一种瞎写法。
  2) 同一个动作失败两次，就必须换路径，不许第三次原样重试。
  3) 判断"成功"要有第二个证据，不能只看返回的 ok。
  4) 不向用户汇报中间失败。对用户只报最终结果，或确实无解时的一句话。
  5) 不要把工具问题说成"网络问题"，也不要把网络问题说成工具坏了。
     先看证据：ssh 通不通 / 端口在不在 / 状态绿不绿。

★ 一句话原则
  能用一条命令验证的，就不要猜；能看日志的，就不要假设。

【附录 D · 只接受密码的主机怎么连（不堵死 MCP）】
============================================================
    # 1. 沙箱侧建转发（注意：不要直接交互式 ssh 到那台机器）
    ssh -F ~/.ssh/config -f -N -L 12222:<目标IP>:22 \
        -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=no \
        -o UserKnownHostsFile=/dev/null local-windows

    # 2. 沙箱侧用 paramiko 带密码
    python3 - <<'PY'
    import paramiko
    c = paramiko.SSHClient(); c.set_missing_host_key_policy(paramiko.AutoAddPolicy())
    c.connect("127.0.0.1", port=12222, username="<用户>", password="<密码>",
              timeout=20, allow_agent=False, look_for_keys=False)
    i,o,e = c.exec_command("hostname; uname -sr")
    print(o.read().decode())
    c.close()
    PY

注意：密码里若有 @ 等特殊字符，必须以字符串原样传入，不要拼进 shell。
